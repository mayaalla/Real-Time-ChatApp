────────────────────────────────────────────────────────────────────────────────
2.1  PublicUser  (the ONLY safe user shape — never expect more fields)
────────────────────────────────────────────────────────────────────────────────
  {
    id:            string   // UUID
    username:      string   // public handle, 3-20 chars
    avatarAddress: string | null  // nullable URL, may be null
    lastSeen:      string | null  // ISO 8601 datetime OR null (never seen)
  }

⚠️  NEVER expect email, passwordHash, name, createdAt from the server.
    These fields are intentionally stripped before any user data leaves the server.
    If you need to display a name, use `username`.

────────────────────────────────────────────────────────────────────────────────
2.2  Conversation
────────────────────────────────────────────────────────────────────────────────
  {
    id:             string   // UUID
    isGroup:        boolean
    name:           string | null   // only set for group chats; null for DMs
    createdAt:      string          // ISO 8601
    // When fetched from GET /api/conversations:
    displayName:    string          // server-computed: group name OR other person's username
    displayPicture: string | null   // server-computed: group icon OR other person's avatar
    participants:   PublicUser[]
    lastMessage:    { textBody: string | null, senderId: string, createdAt: string } | null
    unreadCount:    number          // messages with no receipt from current user
  }

────────────────────────────────────────────────────────────────────────────────
2.3  Message
────────────────────────────────────────────────────────────────────────────────
  {
    id:                string          // UUID — CLIENT-GENERATED (see Rule §4.1)
    conversationId:    string          // UUID
    senderId:          string          // UUID
    textBody:          string | null   // null = attachment-only message
    attachments:       string[]        // array of Cloudinary URLs; [] when none
    status:            "SENT" | "DELIVERED" | "READ"
    createdAt:         string          // ISO 8601
    editedAt:          string | null   // null = never edited
    deletedAt:         string | null   // null = not deleted; if set, show placeholder
    sender?:           PublicUser      // included in REST history, may be absent in socket events
  }

  Visual rendering rules:
    deletedAt !== null  → show "message deleted" placeholder, NOT the textBody
    editedAt !== null   → show "edited" indicator next to the message
    status === "SENT"   → one grey tick  (✓)
    status === "DELIVERED" → two grey ticks  (✓✓)
    status === "READ"   → two blue ticks  (✓✓ in blue)

────────────────────────────────────────────────────────────────────────────────
2.4  Message Status States
────────────────────────────────────────────────────────────────────────────────
  SENT      → saved to DB, not yet delivered to any recipient device
  DELIVERED → reached at least one open device/tab of each recipient
  READ      → recipient SAW it on screen (tab focused + in viewport)

  ⚠️  Status never goes backwards. DELIVERED cannot become SENT. READ cannot
      become DELIVERED. Always guard: only update if new status > current status.

╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
3.1  TOKEN STORAGE — ABSOLUTE RULE
────────────────────────────────────────────────────────────────────────────────
⚠️  ACCESS TOKEN MUST BE STORED IN MEMORY ONLY — NEVER IN localStorage or sessionStorage.

  Correct:   let accessToken: string | null = null;  // module-level variable
  Correct:   Zustand store field  (in-memory)
  WRONG:     localStorage.setItem("accessToken", ...)
  WRONG:     sessionStorage.setItem("accessToken", ...)

  Reason: localStorage/sessionStorage are XSS attack targets. An injected script
  can steal the token. In-memory storage survives page focus changes but is
  cleared on page refresh — this is intentional and safe. The HttpOnly cookie
  restores the session on refresh automatically.

────────────────────────────────────────────────────────────────────────────────
3.2  LOGIN / REGISTER FLOW
────────────────────────────────────────────────────────────────────────────────
POST /api/auth/register   body: { email, username, password }
POST /api/auth/login      body: { email?, username?, password }
  (at least one of email or username must be sent with login)

Response body:
  { ok: true, data: { user: PublicUser, accessToken: string } }

Cookie (set automatically by browser, HttpOnly — not readable by JS):
  refreshToken  (SameSite=strict, maxAge=7days)

On success:
  1. Save `accessToken` to your in-memory store / Zustand store
  2. Save `user` (PublicUser) to your auth state
  3. Connect the Socket.IO socket using the accessToken (see §5.1)
  4. Redirect to the chat page

────────────────────────────────────────────────────────────────────────────────
3.3  EVERY AUTHENTICATED HTTP REQUEST
────────────────────────────────────────────────────────────────────────────────
Every request to a protected endpoint MUST include:
  Authorization: Bearer <accessToken>

The access token expires in 15 minutes.

────────────────────────────────────────────────────────────────────────────────
3.4  TOKEN REFRESH FLOW (intercept 401 TOKEN_EXPIRED)
────────────────────────────────────────────────────────────────────────────────
When any API call returns:
  { ok: false, code: "TOKEN_EXPIRED" }

DO THIS:
  1. POST /api/auth/refresh  (no body needed — the HttpOnly cookie is sent automatically)
     Response: { ok: true, data: { accessToken: string } } + new cookie
  2. Update your in-memory accessToken
  3. Retry the original failed request with the new token

If /api/auth/refresh also fails (401):
  → The session is truly expired. Clear all auth state and redirect to login.

⚠️  Implement this as an interceptor/wrapper around your HTTP client so
    ALL requests automatically handle token expiry without duplicating this logic.

────────────────────────────────────────────────────────────────────────────────
3.5  LOGOUT FLOW
────────────────────────────────────────────────────────────────────────────────
POST /api/auth/logout   (no body needed)
Response: 204 No Content

On logout:
  1. Call POST /api/auth/logout
  2. Clear your in-memory accessToken
  3. Clear user state
  4. Disconnect the Socket.IO socket
  5. Redirect to login

────────────────────────────────────────────────────────────────────────────────
3.6  SESSION RESTORE ON PAGE REFRESH
────────────────────────────────────────────────────────────────────────────────
When the page loads fresh (or refreshes):
  1. accessToken is gone (it was in memory)
  2. Call POST /api/auth/refresh immediately on startup
     → If success: you get a new accessToken → session restored → proceed to app
     → If fail: session expired → redirect to login

  Do NOT redirect to login without first attempting the refresh.
  The HttpOnly cookie is still there after a page refresh.

────────────────────────────────────────────────────────────────────────────────
4.1  STANDARD RESPONSE SHAPES — always handle both
────────────────────────────────────────────────────────────────────────────────
Success:
  { ok: true, data: <payload> }       — most endpoints
  204 No Content                       — logout, mark-read

Error:
  { ok: false, code: "ERROR_CODE", message: "Human message" }
  { ok: false, code: "VALIDATION_ERROR", message: "...", errors: [{field, message}] }

Always check `ok` before reading `data`. Never assume a 2xx means success
without checking `ok: true`.

────────────────────────────────────────────────────────────────────────────────
4.2  HTTP STATUS CODES TO HANDLE
────────────────────────────────────────────────────────────────────────────────
  200 — success with body
  201 — created
  204 — success, no body
  400 — validation error → show field errors from `errors` array
  401 — unauthenticated → check `code`:
          TOKEN_EXPIRED   → trigger refresh flow (§3.4)
          MISSING_TOKEN   → redirect to login
          INVALID_TOKEN   → redirect to login
          MALFORMED_TOKEN → redirect to login
  403 — forbidden (you are not a participant) → show access denied
  404 — not found → handle gracefully
  409 — conflict (duplicate email/username on register) → show error to user
  429 — rate limit → show "Too many requests. Please wait." + Retry-After header
  500 — server error → show generic error, do NOT expose server details

────────────────────────────────────────────────────────────────────────────────
4.3  COMPLETE API ROUTE MAP
────────────────────────────────────────────────────────────────────────────────
All routes are relative to http://localhost:4000 (dev)

  No auth required:
    GET  /api/health                              → { ok, uptime, checks }

  Auth endpoints (rate-limited):
    POST /api/auth/register                       body: { email, username, password }
    POST /api/auth/login                          body: { email?, username?, password }
    POST /api/auth/refresh                        (cookie auto-sent)
    POST /api/auth/logout                         (cookie auto-sent)

  Protected (require Authorization: Bearer <token>):
    GET  /api/users/me                            → PublicUser (current user)
    GET  /api/users?search=<text>                 → PublicUser[] (min 2 chars)
    PATCH /api/users/me                           body: { username?, avatarAddress? }

    POST /api/conversations                       body: { participantIds[], isGroup, name? }
    GET  /api/conversations                       → ConversationList[]
    GET  /api/conversations/:id                   → Conversation with participants

    GET  /api/conversations/:id/messages          query: cursor?, limit (1-100, default 50)
    POST /api/conversations/:id/read              body: { lastReadMessageId }
    POST /api/conversations/:id/messages          body: { textBody?, attachments? }
    DELETE /api/conversations/messages/:messageId (soft delete)
    PATCH  /api/conversations/messages/:messageId body: { textBody }

    POST /api/uploads/sign                        body: { fileName, fileType, fileSize, conversationId }

────────────────────────────────────────────────────────────────────────────────
4.4  MESSAGE HISTORY PAGINATION RULES
────────────────────────────────────────────────────────────────────────────────
The backend uses CURSOR pagination — NEVER page numbers.

GET /api/conversations/:id/messages?cursor=<ISO-datetime>&limit=50

Response:
  { ok: true, data: { messages: Message[], nextCursor: string | null, hasMore: boolean } }

Rules:
  ① First load: call with NO cursor → returns the 50 newest messages
  ② "Load earlier" / infinite scroll upward:
       pass cursor = nextCursor from the previous response
  ③ The backend returns messages newest-first.
     The frontend MUST REVERSE the array before rendering
     (so oldest appears at the top of the chat window).
  ④ When hasMore is false, you have reached the beginning. Stop paginating.
  ⑤ Integrate with React Query using `useInfiniteQuery` for automatic
     page stitching and cache management.

────────────────────────────────────────────────────────────────────────────────
4.5  CONVERSATION CREATION RULES
────────────────────────────────────────────────────────────────────────────────
POST /api/conversations
  body: {
    participantIds: string[],   // UUIDs of OTHER users (current user added automatically)
    isGroup: boolean,
    name?: string               // required for group, ignored for DM
  }

DM rules (isGroup: false):
  - participantIds must contain exactly ONE other user ID
  - Do NOT send a name field
  - If a DM between these two users already exists, the backend returns
    the existing conversation (idempotent) — do NOT create a duplicate

Group rules (isGroup: true):
  - participantIds must contain 2+ other user IDs (3+ total including you)
  - Must include a name

────────────────────────────────────────────────────────────────────────────────
4.6  FILE UPLOAD FLOW (three-step presigned upload)
────────────────────────────────────────────────────────────────────────────────
Files NEVER pass through your code via the socket. Follow these exact steps:

STEP 1 — Get a signed URL from backend:
  POST /api/uploads/sign
  body: {
    fileName:       string,   // original filename
    fileType:       string,   // MIME type (must be in allowed list below)
    fileSize:       number,   // bytes (integer, max 10 MB = 10 * 1024 * 1024)
    conversationId: string,   // UUID
  }
  Response: {
    uploadUrl:  string,   // POST the file bytes here (direct to Cloudinary)
    publicUrl:  string,   // permanent URL after upload completes
    expiresAt:  string,   // ISO datetime — signature expires in 10 min
    signature:  string,
    timestamp:  number,
    apiKey:     string,
    folder:     string,
    publicId:   string,
  }

STEP 2 — Upload the file DIRECTLY to Cloudinary (NOT through your backend):
  POST <uploadUrl> with FormData containing the file bytes

STEP 3 — Use publicUrl in the message:
  Include the publicUrl in the attachments[] array when sending the message

Allowed file types:
  image/jpeg, image/png, image/gif, image/webp, image/svg+xml,
  application/pdf, text/plain, application/msword,
  application/vnd.openxmlformats-officedocument.wordprocessingml.document

Maximum file size: 10 MB (10 * 1024 * 1024 bytes)
Reject files larger than this BEFORE calling the signing endpoint.

────────────────────────────────────────────────────────────────────────────────
4.7  GENERAL API RATE LIMITS
────────────────────────────────────────────────────────────────────────────────
  All /api/* routes:        100 requests per minute per IP
  Auth endpoints:           5 attempts per 15 minutes per IP

  On 429 response:
    - Read the Retry-After header for exact wait time
    - Show a user-friendly "Too many requests, please wait X seconds" message
    - Do NOT automatically retry without waiting

────────────────────────────────────────────────────────────────────────────────
5.1  CONNECTING — EXACT REQUIREMENTS
────────────────────────────────────────────────────────────────────────────────
The socket MUST be created with these exact options:

  import { io } from "socket.io-client";

  const socket = io("http://localhost:4000", {
    auth: { token: getAccessToken() },   // ← accessToken in auth.token
    transports: ["websocket"],           // ← REQUIRED: skip HTTP polling
    reconnection: true,
    reconnectionDelay:    1_000,
    reconnectionDelayMax: 10_000,
    reconnectionAttempts: Infinity,
  });

  ⚠️  NEVER put the token in the query string:
      WRONG: io("http://localhost:4000?token=xxx")  ← ends up in server logs
      RIGHT: io("http://localhost:4000", { auth: { token: xxx } })

  ⚠️  transports: ["websocket"] is MANDATORY.
      Without it, Socket.IO tries HTTP polling first, which breaks load balancing
      (the "sticky session" problem). The backend is designed for WebSocket only.

────────────────────────────────────────────────────────────────────────────────
5.2  AUTHENTICATION ERRORS ON CONNECT
────────────────────────────────────────────────────────────────────────────────
  socket.on("connect_error", async (err) => {
    if (err.message.includes("AUTH_MISSING")) {
      // No token — redirect to login
    }
    if (err.message.includes("AUTH_INVALID") || err.message.includes("TOKEN_EXPIRED")) {
      // Token expired — try to refresh first, then reconnect
      try {
        await refreshAccessToken();          // POST /api/auth/refresh
        socket.auth = { token: getAccessToken() };   // update socket auth
        socket.connect();                    // retry connection
      } catch {
        // Refresh also failed → session truly expired
        redirectToLogin();
      }
    }
  });

────────────────────────────────────────────────────────────────────────────────
5.3  EVENT NAMES — EXACT STRINGS (copy from backend events.ts)

Define these constants in your frontend too. NEVER type the strings by hand.

────────────────────────────────────────────────────────────────────────────────
5.4  EVENT PAYLOADS — EXACT SHAPES
────────────────────────────────────────────────────────────────────────────────

CLIENT → SERVER payloads (what YOU send):

  conversation:join     → { conversationId: string }   // UUID
  conversation:leave    → { conversationId: string }   // UUID
  message:send          → {
                            id: string,              // UUID — CLIENT-GENERATED
                            conversationId: string,  // UUID
                            textBody?: string,       // optional, max 2000 chars
                            attachments?: string[],  // optional, array of URLs
                          }
                          // at least one of textBody or attachments required
  message:read          → { conversationId: string, lastReadMessageId: string }
  typing:start          → { conversationId: string }
  typing:stop           → { conversationId: string }
  sync:since            → { conversationId: string, since: string }  // since = last msg UUID
  presence:fetch        → (no payload)   // ask for snapshot of all contacts' presence

SERVER → CLIENT payloads (what YOU receive):

  message:new           → { message: { id, conversationId, senderId, textBody, attachments,
                                       status, createdAt } }
  message:status        → { messageId: string, status: "SENT"|"DELIVERED"|"READ",
                            userId: string }
  typing:update         → { conversationId: string, typerIds: string[] }
  presence:update       → { userId: string, online: boolean, lastSeen: string | null }
  conversation:created  → { conversation: { id, isGroup, name, createdAt } }
  error                 → { code: string, message: string }
  conversation:joined   → { conversationId: string }
  sync:messages         → { conversationId: string, messages: Message[] }
  sync:reload           → { conversationId: string }
  presence:snapshot     → Array<{ userId: string, online: boolean }>
  conversation:unread_count → { conversationId: string, unreadCount: number }

────────────────────────────────────────────────────────────────────────────────
5.5  MESSAGE:NEW — DE-DUPLICATION RULE (CRITICAL)
────────────────────────────────────────────────────────────────────────────────
⚠️  A user who IS in the conversation room can receive message:new TWICE:
    Once from the conversation room broadcast (Step 7 in server code)
    Once from their personal user room broadcast (Step 8 in server code)

The frontend MUST de-duplicate by message.id BEFORE adding to the store.
  if (!messageExistsInStore(message.id)) {
    addMessageToStore(message);
  }

Also: when you send a message and get message:new back as the ack, do not
add a duplicate if you already have it as a PENDING optimistic message.
Match by id and replace the PENDING entry.

────────────────────────────────────────────────────────────────────────────────
5.6  ROOM MANAGEMENT
────────────────────────────────────────────────────────────────────────────────
Room strategy: JOIN ONE (only the currently open conversation)

When user opens a conversation:
  socket.emit("conversation:join", { conversationId })
  // Wait for "conversation:joined" ack before rendering the live message tail

When user opens a different conversation:
  socket.emit("conversation:leave", { conversationId: previousId })
  socket.emit("conversation:join",  { conversationId: newId })

When user goes to a non-conversation screen (settings, etc.):
  socket.emit("conversation:leave", { conversationId: currentId })

The user's personal room (user:{userId}) is auto-joined by the server on
socket connect — you do NOT need to emit anything for it.
It is used for: message:new for conversations you are NOT currently viewing,
message:status, presence:update, conversation:created, conversation:unread_count.

║  PART 6 — SENDING MESSAGES — COMPLETE FLOW                                   ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
6.1  CLIENT-GENERATED MESSAGE ID — ABSOLUTE RULE
────────────────────────────────────────────────────────────────────────────────
⚠️  The MESSAGE ID IS GENERATED BY THE CLIENT, not the server.
    You MUST use a UUID library to generate it BEFORE emitting.

  import { v4 as uuidv4 } from "uuid";
  const messageId = uuidv4();

  Why: If the socket disconnects mid-send, the client can re-emit the EXACT
  same payload with the SAME id. The server uses upsert (create if not exists)
  so the second send creates zero duplicates. If you change the ID on retry,
  you get a duplicate message in the database.

────────────────────────────────────────────────────────────────────────────────
6.2  OPTIMISTIC SEND (recommended UX pattern)
────────────────────────────────────────────────────────────────────────────────
When user presses Send:
  1. Generate a UUID for the message: const id = uuidv4()
  2. Add the message to the local store immediately with status "PENDING":
       { id, conversationId, senderId: currentUserId, textBody, attachments, status: "PENDING", ... }
  3. Emit: socket.emit("message:send", { id, conversationId, textBody, attachments })
  4. When server sends back message:new with the same id:
       → Replace the PENDING entry with the server's version (has real timestamps and status)
  5. If server responds with error:
       → Mark the message "FAILED" (show retry button)

────────────────────────────────────────────────────────────────────────────────
6.3  OFFLINE MESSAGE QUEUE
────────────────────────────────────────────────────────────────────────────────
If the socket is disconnected when user presses Send:
  1. Generate UUID and add message to local store as "PENDING"
  2. Save the message payload to an offline queue (memory or localStorage)
  3. When the socket reconnects (the "connect" event fires):
     → Flush the queue in order:
         for (const msg of offlineQueue) {
           socket.emit("message:send", msg);   // same UUID → safe upsert on server
         }
         clearOfflineQueue();

⚠️  RULE: Never generate a new UUID on retry. Always re-use the original UUID.
⚠️  RULE: On retry, if the user clicks Retry, re-use the ORIGINAL UUID.

────────────────────────────────────────────────────────────────────────────────
6.4  MESSAGE VALIDATION RULES (enforce in UI before sending)
────────────────────────────────────────────────────────────────────────────────
  - textBody max length: 2000 characters (server rejects longer with VALIDATION_ERROR)
  - textBody min length (if provided): 1 character (no empty strings)
  - attachments: array of strings (URLs) — at least 1 item if provided
  - MUST have at least one of: textBody or attachments (error if both absent)
  - Enforce these in the UI before emitting to avoid unnecessary round-trips

╔══════════════════════════════════════════════════════════════════════════════╗
║  PART 7 — READING MESSAGES — RECEIPT RULES                                   ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
7.1  WHEN TO SEND message:delivered
────────────────────────────────────────────────────────────────────────────────
When your socket receives message:new:
  IMMEDIATELY emit back:
    socket.emit("message:delivered", { messageId: message.id })

This is automatic — the user doesn't need to do anything to trigger it.
The server will then emit message:status { status: "DELIVERED" } to the sender.

────────────────────────────────────────────────────────────────────────────────
7.2  WHEN TO SEND message:read — ALL FOUR RULES MUST BE RESPECTED
────────────────────────────────────────────────────────────────────────────────

RULE 1 — Only when the browser tab is FOCUSED:
  Check: document.hasFocus()
  Listen: window.addEventListener("focus", ...) and window.addEventListener("blur", ...)
  If the user is in another tab or another app: DO NOT send message:read.

RULE 2 — Only when the message is actually VISIBLE on screen:
  Use the Intersection Observer API.
  DO NOT send message:read just because the chat loaded.
  The user must scroll to (or already see) the message in the viewport.

RULE 3 — Debounce / group the claims:
  DO NOT send one message:read per message as the user scrolls.
  Wait ~300ms after the last scroll event, then send ONE event with the
  ID of the NEWEST message currently visible in the viewport.
  The server marks everything up to that point as read in one operation.

RULE 4 — Track the newest visible message ID:
  Use a ref/state to track the newest message ID currently in the viewport.
  Update it as the user scrolls. When the debounce fires, send that ID.

  socket.emit("message:read", {
    conversationId: currentConversationId,
    lastReadMessageId: newestVisibleMessageId,
  });

────────────────────────────────────────────────────────────────────────────────
7.3  UPDATING UI ON message:status
────────────────────────────────────────────────────────────────────────────────
  socket.on("message:status", ({ messageId, status, userId }) => {
    // Find the message in local store by messageId
    // Update its status — BUT ONLY if the new status is "higher" than current:
    //   SENT < DELIVERED < READ
    // Never downgrade a status (READ should never become DELIVERED)
    updateMessageStatus(messageId, status);
  });

────────────────────────────────────────────────────────────────────────────────
7.4  UNREAD COUNT
────────────────────────────────────────────────────────────────────────────────
  Unread count is derived from the receipts table on the server — NEVER store
  it as a counter you increment by hand (it will drift).

  Sources of unread count truth:
    ① GET /api/conversations returns unreadCount per conversation (REST initial load)
    ② conversation:unread_count socket event fires after you mark messages as read

  When you receive message:new for a conversation you are NOT currently viewing:
    → Increment local badge by 1 (optimistic)
    → Or re-fetch conversation list

  When you mark messages as read (message:read event sent):
    → The server will push conversation:unread_count with the new count
    → Update your store from that event, not by decrementing manually

╔══════════════════════════════════════════════════════════════════════════════╗
║  PART 8 — TYPING INDICATORS                                                  ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
8.1  SENDING TYPING EVENTS — THROTTLE RULE
────────────────────────────────────────────────────────────────────────────────
⚠️  DO NOT send typing:start for every single keystroke.
    Throttle it: send typing:start at most once every 2–3 seconds.

  Logic:
    On keydown:
      if (not currently marked as typing):
        socket.emit("typing:start", { conversationId })
        mark yourself as typing
        start/reset a 3-second timer:
          after 3s of no keydown → socket.emit("typing:stop", { conversationId })
          clear typing state
      else:
        reset/extend the 3-second timer (do NOT re-emit typing:start)

  On message send:
    socket.emit("typing:stop", { conversationId })
    clear typing state and timer immediately

  On input clear:
    socket.emit("typing:stop", { conversationId })

────────────────────────────────────────────────────────────────────────────────
8.2  RECEIVING TYPING EVENTS
────────────────────────────────────────────────────────────────────────────────
  socket.on("typing:update", ({ conversationId, typerIds }) => {
    // typerIds is an array of userIds currently typing in this conversation
    // Filter out your own userId
    const othersTyping = typerIds.filter(id => id !== currentUserId);
    // Update your Zustand store with othersTyping for this conversationId
    // Display "Alice is typing..." or "Alice and Bob are typing..."
  });

  The server sets a 5-second TTL on the typing key. If a user closes their
  laptop mid-sentence, the indicator disappears automatically within 5 seconds
  WITHOUT receiving a typing:stop event. So DO NOT depend on typing:stop to
  clear the indicator — it can vanish at any time via the TTL.

╔══════════════════════════════════════════════════════════════════════════════╗
║  PART 10 — RECONNECTION RULES                                                ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
10.1  ON EVERY SUCCESSFUL RECONNECT — DO ALL OF THESE
────────────────────────────────────────────────────────────────────────────────
The "connect" event fires on FIRST connect AND every reconnect. Use it for both.

  socket.on("connect", async () => {
    // Step 1: Re-join the currently open conversation room
    if (currentConversationId) {
      socket.emit("conversation:join", { conversationId: currentConversationId });
    }

    // Step 2: Sync missed messages (if a conversation is open)
    if (currentConversationId) {
      const lastMessageId = getLastMessageIdForConversation(currentConversationId);
      if (lastMessageId) {
        socket.emit("sync:since", {
          conversationId: currentConversationId,
          since: lastMessageId,   // UUID of last message you have
        });
      }
    }

    // Step 3: Refresh presence snapshot
    socket.emit("presence:fetch");

    // Step 4: Flush the offline message queue (if any)
    const queue = getOfflineMessageQueue();
    for (const msg of queue) {
      socket.emit("message:send", msg);  // same UUID → safe
    }
    clearOfflineMessageQueue();
  });

────────────────────────────────────────────────────────────────────────────────
10.2  HANDLING sync:since RESPONSE
────────────────────────────────────────────────────────────────────────────────
  socket.on("sync:messages", ({ conversationId, messages }) => {
    for (const message of messages) {
      if (!messageExistsLocally(message.id)) {   // de-duplicate by ID
        addMessageToStore(conversationId, message);
      }
    }
  });

  socket.on("sync:reload", ({ conversationId }) => {
    // Server says there are too many missed messages (>200) to send over socket
    // Fall back to REST: fetch the conversation history from scratch
    fetchConversationHistory(conversationId);  // GET /api/conversations/:id/messages
    // This replaces the entire cached message list for this conversation
  });

  The "since" field in sync:since is the UUID of the last message you have
  locally (NOT a timestamp). The server uses it to find the timestamp, then
  returns all newer messages.

────────────────────────────────────────────────────────────────────────────────
12.1  USER SEARCH
────────────────────────────────────────────────────────────────────────────────
GET /api/users?search=<text>

Rules:
  - Minimum 2 characters before sending the request (enforce in UI)
  - Debounce the input (~300ms) to avoid spamming the server
  - The server searches by username only (case-insensitive prefix match)
  - The server excludes the current user from results
  - Returns up to ~20 results (PublicUser[])
  - Email is NOT searchable and NOT returned

────────────────────────────────────────────────────────────────────────────────
12.2  WHAT TO DISPLAY FOR A USER
────────────────────────────────────────────────────────────────────────────────
  Display name: always use `username`
  Avatar:       use `avatarAddress` if not null, else show initials/placeholder
  Last seen:    if `lastSeen` is null → show "Never seen" or hide
                if `lastSeen` is set → show relative time (e.g. "2 hours ago")

║  PART 13 — SECURITY RULES (WHAT THE FRONTEND MUST NEVER DO)                  ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
13.1  ABSOLUTE PROHIBITIONS
────────────────────────────────────────────────────────────────────────────────
❌  NEVER store accessToken in localStorage or sessionStorage
❌  NEVER put the accessToken in a URL query string
❌  NEVER trust data from socket event payloads for user identity
    (userId comes from the JWT in socket.data, not from the event payload)
❌  NEVER include email, passwordHash, name, or createdAt in expected API responses
    (these fields don't exist in the PublicUser shape returned by the backend)
❌  NEVER hard-delete message rows or expect them to be absent after delete
    (soft delete: deletedAt is set, the row stays — show placeholder)
❌  NEVER build a rate limiter into the frontend to "help" the backend
    (the backend has its own; the frontend just handles 429 responses gracefully)
❌  NEVER generate a new UUID when retrying a failed/pending message
    (always re-use the original UUID to prevent duplicates)

────────────────────────────────────────────────────────────────────────────────
13.2  INPUT VALIDATION (client-side — enforce before sending)
────────────────────────────────────────────────────────────────────────────────
Registration:
  email: must be valid email format
  username: 3-20 chars, only a-zA-Z0-9._
  password: min 8 chars

Message text:
  max 2000 characters (server rejects longer — show counter in UI)
  min 1 character if provided

File uploads:
  max 10 MB (reject before signing request)
  only allowed MIME types (see §4.6)

User search:
  min 2 characters before querying

║  PART 14 — ERROR HANDLING GUIDE                                              ║
╚══════════════════════════════════════════════════════════════════════════════╝

────────────────────────────────────────────────────────────────────────────────
14.1  HTTP ERROR CODES → UI BEHAVIOR
────────────────────────────────────────────────────────────────────────────────
  401 + code "TOKEN_EXPIRED"    → silently refresh token and retry request
  401 + other codes             → redirect to login screen
  400 + code "VALIDATION_ERROR" → show field-level errors from `errors` array
  409 + "CONFLICT"              → show "Username or email already taken"
  403                           → show "You don't have access to this"
  404                           → show "Not found" or navigate away
  429                           → show rate limit message + countdown from Retry-After header
  500                           → show generic "Something went wrong" message
                                  DO NOT show server error details to user

────────────────────────────────────────────────────────────────────────────────
14.2  SOCKET ERROR EVENT
────────────────────────────────────────────────────────────────────────────────
  socket.on("error", ({ code, message }) => {
    switch (code) {
      case "NOT_MEMBER":
        // User is not in this conversation — remove from UI or show error
        break;
      case "VALIDATION_ERROR":
        // Show the message to the user (but this shouldn't happen if UI validates)
        break;
      case "TOO_MANY_REQUESTS":
        // Show "Slow down" message to user
        // Disable send button briefly
        break;
      case "HANDLER_ERROR":
        // Generic server error — log it, show "Something went wrong"
        break;
    }
  });

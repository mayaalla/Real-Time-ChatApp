────────────────────────────────────────────────────────────────────────────────
1.1  WHAT THIS PROJECT IS
────────────────────────────────────────────────────────────────────────────────
A real-time chat application backend built as a portfolio project.
Goal: demonstrate a production-grade Node.js backend with WebSocket messaging,
JWT auth, PostgreSQL via Prisma, Redis pub/sub for horizontal scaling, and
correct handling of edge cases (duplicate messages, reconnection, presence, etc.)

This project is NOT finished. It is being built incrementally following a
detailed 28-part build plan (see /Chatapp/tasks.md).

────────────────────────────────────────────────────────────────────────────────
1.2  TECH STACK (EXACT VERSIONS)
────────────────────────────────────────────────────────────────────────────────
Runtime        : Node.js 20+, TypeScript 5.x (strict mode)
Language mode  : ESM ("type": "module" in package.json)
Framework      : Express 5.x (async error forwarding built-in)
Database       : PostgreSQL via Neon (serverless Postgres, cloud-hosted)
ORM            : Prisma 7.x with @prisma/adapter-pg (driver adapter required)

Dev runner     : tsx (watch mode for hot reload)

Linter         : ESLint 10 + typescript-eslint

2.2  MODELS
────────────────────────────────────────────────────────────────────────────────

MODEL: User
  id            String   @id @default(uuid())
  email         String   @unique
  name          String                          ← display name (editable, defaults to username)
  username      String   @unique               ← public handle, 3-20 chars
  passwordHash  String                          ← bcrypt hash, NEVER returned to clients
  avatarAddress String?                         ← nullable URL
  lastSeen      DateTime?                       ← null = never seen after signup; updated on login/disconnect
  createdAt     DateTime @default(now())
  Relations: participants[], messages[], receipt[], token[]

MODEL: Conversation
  id        String   @id @default(uuid())
  isGroup   Boolean  @default(false)
  name      String?                             ← only set when isGroup=true; DMs have no name
  createdAt DateTime @default(now())
  Relations: participants[], messages[]

ENUM: Role  (on Participant)
  OWNER    ← created the conversation; can add/remove/rename
  ADMIN    ← can add/remove members; cannot remove OWNER
  MEMBER   ← default for new participants

MODEL: Participant  (join table — makes group chat work)
  id             String   @id @default(uuid())
  role           Role     @default(MEMBER)
  joinTime       DateTime @default(now())
  userId         String   → User.id
  conversationId String   → Conversation.id
  @@unique([userId, conversationId])            ← cannot join same convo twice
  @@index([conversationId])                     ← fast "who is in this chat?"

ENUM: Status  (on Message)
  SENT         ← saved to DB, not yet delivered
  DELIVERED    ← received by recipient's socket
  READ         ← recipient opened and read it

MODEL: Message
  id                String   @id                ← CLIENT-GENERATED UUID (critical design decision)
  senderId          String   → User.id
  conversationId    String   → Conversation.id
  textBody          String?                      ← nullable (attachment-only message is valid)
  attachmentAddress String?                      ← nullable URL (Cloudinary / S3)
  status            Status   @default(SENT)
  createdAt         DateTime @default(now())
  editedAt          DateTime?                    ← null means never edited
  deletedAt         DateTime?                    ← soft delete: row stays, body shown as placeholder
  Relations: sender(User), conversation(Conversation), receipt[]
  @@index([conversationId, createdAt(sort: Desc)])  ← THE KEY INDEX for cursor pagination

MODEL: Receipt  (read receipts — one row per user per message)
  messageId String → Message.id
  userId    String → User.id
  readTime  DateTime @default(now())
  @@id([messageId, userId])                     ← composite PK: one receipt per user per message

MODEL: RefreshToken
  token     String   @id                        ← the raw JWT string IS the PK
  ownerId   String   → User.id (cascade delete)
  expiry    DateTime                             ← absolute UTC expiry
  revoked   Boolean  @default(false)
  createdAt DateTime @default(now())
  @@index([ownerId])                             ← fast "all tokens for user X" (logout-all)
  @@index([expiry])                              ← fast sweep of expired rows

────────────────────────────────────────────────────────────────────────────────
2.3  CRITICAL DATABASE DESIGN DECISIONS (DO NOT REVERSE)
────────────────────────────────────────────────────────────────────────────────
1. MESSAGE ID IS CLIENT-GENERATED
   The frontend creates the UUID before sending. This makes retry-on-reconnect
   safe: re-sending the same event creates zero duplicates because the INSERT
   uses the pre-existing ID and is ignored (upsert pattern / conflict handling).
   If you change this to server-generated, you BREAK reconnection re-sends.

2. SOFT DELETE ON MESSAGES
   deletedAt is set, row is kept. Return "message deleted" placeholder.
   Do NOT hard-delete messages or you break receipt counts and thread ordering.

3. COMBINED INDEX ON (conversationId, createdAt DESC)
   This is what makes cursor pagination O(log n) instead of O(n).
   Cursor = "give me messages older than this createdAt in this conversation".
   If you remove this index, message history queries will table-scan.

4. REFRESH TOKEN TABLE (not Redis)
   Decision: store refresh tokens in Postgres, not Redis.
   Reason: easier to inspect, easier to revoke individual sessions.
   Trade-off: tokens are not auto-deleted; expired rows accumulate.
   Clean-up strategy: WHERE expiry > NOW() AND revoked = FALSE at query time.
   A periodic job or a DELETE on login should sweep stale rows.

5. PARTICIPANT TABLE IS THE AUTH MODEL FOR ROOMS
   Before anyone joins a socket room or reads messages, check Participant table.
   There is one shared function for this check (see Part 3.5).
   Never inline the membership check. Never trust a user-supplied conversationId.

────────────────────────────────────────────────────────────────────────────────
3.5  src/middleware/authenticate.ts   (COMPLETE)
────────────────────────────────────────────────────────────────────────────────
Express middleware that guards protected routes.

Flow:
  1. Read Authorization header → extract "Bearer <token>"
  2. verifyAccessToken(token) → VerifyResult
  3. On failure → 401 with specific code:
       MISSING_TOKEN   — no header / wrong format
       TOKEN_EXPIRED   — valid signature but exp passed (frontend should refresh)
       INVALID_TOKEN   — bad signature, malformed JWT
       MALFORMED_TOKEN — valid sig but missing sub or username fields
  4. On success → cast req to AuthenticatedRequest, attach user, call next()

The req.user object attached:
  { id: string, email: string, username: string }
  Note: email is set to "" (empty string) — it's not embedded in the JWT.
  If a handler needs the actual email, it must fetch from DB using req.user.id.

Usage in routes:
  router.get("/me", authenticate, meController)
  router.use(authenticate)  // protect entire router

3.8  src/modules/auth/ — ALL FILES COMPLETE
────────────────────────────────────────────────────────────────────────────────

auth.schemas.ts:
  PublicUserSchema / PublicUser — { id, username, avatarAddress, lastSeen }
    → The canonical safe user shape. Use this EVERYWHERE user data leaves the server.
    → Never expose: email, passwordHash, name (for now), createdAt
  RegisterBodySchema / RegisterBody — { email, username, password }
    → email: trimmed, lowercased, valid email format
    → username: 3-20 chars, /^[a-zA-Z0-9._]+$/ only
    → password: min 8 chars
  LoginBodySchema / LoginBody — { email?, username?, password }
    → email OR username must be present (enforced by .superRefine)
    → both are optional individually; at least one required together

auth.service.ts — custom error classes:
  ConflictError    (statusCode 409) — email or username already taken
  UnauthorisedError (statusCode 401) — bad credentials
  InvalidRefreshTokenError (statusCode 401) — bad/expired/revoked refresh token

auth.service.ts — exported functions:
  toPublicUser(user) → PublicUser
    → strips all private fields, returns only PublicUser shape
    → called EVERYWHERE a user object is returned to any client
  registerUser(body: RegisterBody) → { user, accessToken, refreshToken }
    → checks email/username uniqueness (single OR query, no field hint leak)
    → hashes password (bcrypt cost 12)
    → creates User in DB
    → issues token pair (saves refresh token to RefreshToken table)
    → returns PublicUser + both tokens
  loginUser(body: LoginBody) → { user, accessToken, refreshToken }
    → finds user by email OR username (single OR query)
    → ALWAYS runs bcrypt.compare even if user not found (timing-safe)
    → uses DUMMY_HASH "$2b$12$invalidsalt..." for constant time on missing users
    → updates lastSeen (fire-and-forget, failure silently ignored)
    → returns PublicUser + both tokens
  refreshSession(rawToken) → { accessToken, refreshToken }
    → verifies JWT signature
    → checks DB row: exists, same owner, not revoked, not expired
    → revokes old token BEFORE creating new one
    → returns fresh token pair
  logoutUser(rawToken) → void
    → verifies JWT (but does NOT throw on expired — logout always clears cookie)
    → updateMany where token + ownerId + revoked=false → set revoked=true
    → silent on missing rows

auth.controller.ts — four controllers:
  registerController → POST /api/auth/register
    → 201 + { ok, data: { user, accessToken } } + refreshToken in HttpOnly cookie
    → 409 on ConflictError
  loginController → POST /api/auth/login
    → 200 + { ok, data: { user, accessToken } } + refreshToken in HttpOnly cookie
    → 401 on UnauthorisedError (generic message, no field hint)
  refreshController → POST /api/auth/refresh
    → reads refreshToken cookie
    → 200 + { ok, data: { accessToken } } + new cookie
    → 401 + clearCookie on any failure
  logoutController → POST /api/auth/logout
    → always 204 + clearCookie (even if cookie was missing)

REFRESH COOKIE OPTIONS (applied consistently across all auth controllers):
  { httpOnly: true, secure: (production only), sameSite: "strict", maxAge: 7 days }

auth.routes.ts:
  POST /api/auth/register  → withRateLimit(registerLimiter) → validate(RegisterBodySchema) → registerController
  POST /api/auth/login     → withRateLimit(loginLimiter) → validate(LoginBodySchema) → loginController
  POST /api/auth/refresh   → withRateLimit(refreshLimiter) → refreshController
  POST /api/auth/logout    → logoutController (no rate limit — always safe)
  Mounted at: /api/auth in app.ts

5.1  STANDARD RESPONSE SHAPES
────────────────────────────────────────────────────────────────────────────────
All responses follow these shapes consistently:

Success:
  { ok: true, data: <payload> }                 ← for GET/POST with body
  204 No Content                                ← for logout / delete

Error:
  { ok: false, code: "ERROR_CODE", message: "Human message" }
  { ok: false, code: "VALIDATION_ERROR", message: "...", errors: [{field, message}] }

HTTP status codes used:
  200 — success with body (login, refresh, GET endpoints)
  201 — created (register, create conversation, create message via REST)
  204 — success, no body (logout, mark-read)
  400 — validation error (Zod failures)
  401 — unauthenticated (missing/invalid/expired token)
  403 — forbidden (authenticated but not authorized — not a participant)
  404 — not found
  409 — conflict (duplicate email/username)
  429 — too many requests (rate limit hit)
  503 — service unavailable (DB down on health check)
  500 — unexpected server error

5.3  TOKEN / COOKIE FLOW (for any front-end that connects to this API)
────────────────────────────────────────────────────────────────────────────────
Login / Register response:
  → Body contains: { ok, data: { user: PublicUser, accessToken: string } }
  → Cookie set: "refreshToken" (HttpOnly, SameSite=strict, maxAge=7days)
  → Client stores accessToken in MEMORY only (never localStorage, never sessionStorage)

Every authenticated request:
  → Header: Authorization: Bearer <accessToken>
  → Access token expires in 15 minutes

When access token expires:
  → Server returns: { ok: false, code: "TOKEN_EXPIRED" }
  → Client POSTs to /api/auth/refresh (cookie sent automatically)
  → Response: { ok, data: { accessToken } } + new cookie
  → Client retries original request with new token

Socket.IO connection:
  → Pass access token in: io({ auth: { token: accessToken } })
  → NOT in query string (ends up in logs)
  → Use same verifyAccessToken helper on server side

────────────────────────────────────────────────────────────────────────────────
6.1  MODULE PATTERN (enforced in every feature folder)
────────────────────────────────────────────────────────────────────────────────
Every feature module has EXACTLY 4 files:
  *.routes.ts     → lists URLs, middleware, and handlers. ZERO logic.
  *.controller.ts → reads validated req, calls service, sends response.
                    NO database calls. NO business logic.
  *.service.ts    → all DB access, all business logic. Knows nothing about HTTP.
                    (no req, no res, no status codes)
  *.schemas.ts    → Zod schemas for inputs and output shapes.

This pattern is non-negotiable. Auth module already follows it correctly.
All future modules (users, conversations, messages) must follow it identically.

────────────────────────────────────────────────────────────────────────────────
6.2  SECURITY DECISIONS (DO NOT CHANGE without understanding why)
────────────────────────────────────────────────────────────────────────────────
1. TIMING-SAFE LOGIN
   Login always runs bcrypt.compare even when no user found. Uses DUMMY_HASH
   so response time is identical for "wrong password" and "no such user".
   Both return the same "Invalid credentials" message.
   Never add early returns before bcrypt in loginUser.

2. NO EMAIL ENUMERATION
   Register: "already taken" message reveals nothing about which field matched.
   Login: generic "Invalid credentials" — same for bad email and bad password.

3. REFRESH TOKEN IN HTTPONLY COOKIE
   - Cannot be read by JavaScript (XSS resistant)
   - Token rotation on every use (replay the old token → 401 + revoke all)
   - Stored in Postgres RefreshToken table with expiry + revoked flag
   - Verify both JWT signature AND DB row before issuing new pair

4. ACCESS TOKEN IN MEMORY ONLY
   Never store in localStorage/sessionStorage. If page refreshes, token is
   gone — this is intentional. The HttpOnly refresh cookie restores the session.

5. TWO SEPARATE JWT SECRETS
   JWT_ACCESS_SECRET ≠ JWT_REFRESH_SECRET
   A leaked refresh secret cannot forge access tokens and vice versa.

6. NEVER TRUST EVENT PAYLOAD USER IDs
   In socket handlers, user identity comes from socket.data (set at auth time).
   Never read userId from the event payload itself.

────────────────────────────────────────────────────────────────────────────────
6.3  REALTIME ARCHITECTURE (for when Socket.IO is implemented)
────────────────────────────────────────────────────────────────────────────────
Room strategy (chosen approach):
  - One room per conversation: named by conversationId
  - One room per user: named by userId (for cross-device notifications)
  - Join conversation room on "conversation:join" event
  - Auto-join user room on socket connect

State ownership (DO NOT MIX these):
  React Query owns: message history (cache, keyed by conversation)
  Socket drives: live tail (writes INTO React Query cache, not separate state)
  Zustand owns: connection status, typing indicators, presence, unsent queue

De-duplication rule: EVERY cache write checks message.id before inserting.
This is the rule that makes optimistic sending safe.

Socket error handling:
  Express 5 auto-forwards async errors in route handlers.
  Socket.IO handlers are NOT covered — every handler needs try/catch.
  On failure: emit "error" event to that socket + log server-side + stay alive.

────────────────────────────────────────────────────────────────────────────────
6.4  HORIZONTAL SCALING DESIGN
────────────────────────────────────────────────────────────────────────────────
Goal: 2+ instances behind a load balancer, sharing one Postgres + one Redis.

Why it breaks without Redis adapter:
  Each instance only knows its own sockets.
  If Alice is on instance 1 and Bob is on instance 2, Alice's message never
  reaches Bob without the adapter.

Redis adapter (already installed: @socket.io/redis-adapter):
  - Pub/sub through Redis so all instances share broadcasts
  - Requires TWO Redis clients (publisher + subscriber)
  - Must be wired unconditionally (dev too, not just production)

Sticky sessions issue:
  Socket.IO can fall back to HTTP polling. Polling MUST hit the same instance.
  Solution: force websocket transport only, OR configure load balancer stickiness.
  Write the decision down when Part 18 is implemented.

────────────────────────────────────────────────────────────────────────────────
6.5  CURSOR PAGINATION (the only pagination pattern used in this project)
────────────────────────────────────────────────────────────────────────────────
Never use page numbers for messages. Reason: new messages shift page boundaries.

Cursor = { id: string, createdAt: DateTime } of the oldest message you have.
Query: WHERE conversationId = :id AND createdAt < :cursor.createdAt
       ORDER BY createdAt DESC
       LIMIT :limit + 1   ← fetch one extra to detect hasMore

Response: { messages[], nextCursor: { id, createdAt } | null, hasMore: boolean }
Ordering for client: DB returns newest-first; client reverses to show oldest-at-top.

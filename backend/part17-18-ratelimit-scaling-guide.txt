STEP 17.1 — LIMIT MESSAGES PER SOCKET (Redis rate limiter for message:send)
================================================================================

UNDERSTAND THE PROBLEM FIRST:
  Your current message handler (src/realtime/handlers/message.ts) saves every
  message it receives with zero throttling. A script could send 1000 messages
  per second, flood the database, and bring down the server for everyone.

  Your current rateLimiter.ts (src/utils/rateLimiter.ts) uses a plain JavaScript
  Map (in-memory). That works for ONE server process. When you run TWO instances
  (Part 18), each process has its OWN Map. A spammer can hammer one instance 5
  times and then switch to the other — getting 10 attempts instead of 5.

  The fix: move the counter into Redis, which is shared by ALL instances.
  This is called the "Redis INCR + EXPIRE" pattern. It works like this:

    1. When the user sends a message, ask Redis:
       "How many messages has userId sent in the last 60 seconds?"

    2. Redis says a number. If it is MORE than our limit (e.g. 20), refuse.

    3. If it is within the limit, add 1 to the counter (INCR command).
       On the FIRST message in a window, set the counter to expire after
       60 seconds (EXPIRE command). That way the counter resets automatically.

  Here is the Redis key we already documented in docs/redis-keys.md:
    ratelimit:{userId}:{windowTimestamp}

  The windowTimestamp is calculated like this:
    Math.floor(Date.now() / 1000 / 60) * 60
    That gives us the start of the current 60-second window as a Unix timestamp.
    Example: if it is 14:32:47, the window start is 14:32:00 → 1700000000 (fake).
    Everyone in the same 60-second window shares the SAME counter key.

import { redisClient } from "../redis/client.js";

// ─── WHAT THIS FILE DOES ──────────────────────────────────────────────────────
//
// This is the Redis-backed rate limiter for Socket.IO events.
//
// WHY REDIS AND NOT MEMORY?
//   A JavaScript Map lives in one process only. When you run two server
//   instances, each has its own Map. A spammer can bypass the limit by
//   alternating between instances.
//   Redis is shared by ALL instances → one global counter per user.
//
// HOW IT WORKS (Redis INCR + EXPIRE pattern):
//   Every user gets a counter key in Redis: ratelimit:{userId}:{windowStart}
//   The windowStart is the beginning of the current 60-second window.
//   Each message send increments the counter.
//   The key auto-deletes when the window ends — no cleanup code needed.
//
// ─────────────────────────────────────────────────────────────────────────────

// ─── Config ───────────────────────────────────────────────────────────────────
// How many messages one user can send inside one time window.
export const MSG_LIMIT    = 20;     // 20 messages …
export const MSG_WINDOW_S = 60;     // … per 60 seconds

// Lighter limit for noisy-but-harmless events (typing, join, sync).
export const NOISE_LIMIT    = 60;   // 60 events …
export const NOISE_WINDOW_S = 60;   // … per 60 seconds

// ─── Key builder ──────────────────────────────────────────────────────────────
// Returns the Redis key for this user's counter in the current time window.
// windowSeconds controls the length of each window (60s for messages).

function rateLimitKey(userId: string, windowSeconds: number): string {
  // "What window are we in right now?"
  // Floor the current time to the nearest multiple of windowSeconds.
  // Example: windowSeconds=60  →  every minute gets a new key.
  const windowStart = Math.floor(Date.now() / 1000 / windowSeconds) * windowSeconds;
  return `ratelimit:${userId}:${windowStart}`;
}

// ─── Core function ────────────────────────────────────────────────────────────

/**
 * Check if userId has exceeded limit within windowSeconds.
 *
 * Returns { allowed: true }  if the request should proceed.
 * Returns { allowed: false, retryAfter: number }  if they are over the limit.
 *   retryAfter = seconds until the window resets (for the error message).
 *
 * IMPORTANT: This function ALWAYS increments the counter on every call,
 * even for the first request. Redis INCR creates the key if it doesn't exist.
 * We set EXPIRE only on the FIRST increment (when the counter was just created).
 */
export async function checkSocketRateLimit(
  userId:        string,
  limit:         number,
  windowSeconds: number,
): Promise<{ allowed: boolean; retryAfter: number }> {

  const key = rateLimitKey(userId, windowSeconds);

  // INCR: adds 1 to the counter and returns the new value.
  // If the key did not exist, Redis creates it with value 0 first, then adds 1.
  // Result is the new count (1, 2, 3, … up to limit+1 and beyond).
  const count = await redisClient.incr(key);

  // On first increment (count === 1), set the expiry.
  // We only do this once so we don't accidentally extend the window on every request.
  if (count === 1) {
    await redisClient.expire(key, windowSeconds);
  }

  if (count > limit) {
    // How many seconds until the current window ends?
    // TTL returns the remaining lifetime of the key in seconds.
    const ttl = await redisClient.ttl(key);
    return { allowed: false, retryAfter: Math.max(ttl, 1) };
  }

  return { allowed: true, retryAfter: 0 };
}

  // ── General API rate limit ────────────────────────────────────────────────
  // 100 requests per minute per IP. This applies to ALL /api/* routes.
  // Auth routes have their own stricter limits on top of this.
  const generalApiLimiter = rateLimit({
    windowMs:         60 * 1000,        // 1 minute window
    max:              100,              // max 100 requests per window per IP
    standardHeaders:  true,             // sends RateLimit-* headers in the response
    legacyHeaders:    false,            // turns off the older X-RateLimit-* headers
    message: {
      ok:      false,
      code:    "TOO_MANY_REQUESTS",
      message: "Too many requests. Please slow down and try again in a minute.",
    },
  });

  // Apply the general limiter to all /api routes.
  app.use("/api", generalApiLimiter);

──────────────────────────────────────────────────────────────────────────────

IMPORTANT — ORDER MATTERS:
  Put app.use("/api", generalApiLimiter) BEFORE your route registrations.
  Middleware is executed in the ORDER it is registered.
  If you put it after the routes, it will never run.

  Your app.ts middleware order should look like this:
    1. pinoHttp logger (FIRST — so it logs everything)
    2. cors
    3. helmet
    4. express.json
    5. cookieParser
    6. app.use("/api", generalApiLimiter)   ← NEW
    7. app.use("/api/auth", authRouter)
    8. app.use("/api/users", usersRouter)
    9. app.use("/api/conversations", conversationsRouter)
    10. app.use("/api/messages", messagesRouter)
    11. app.use("/api/uploads", uploadsRouter)
    12. GET /api/health
    13. 404 handler
    14. Global error handler

PART 18 — HORIZONTAL SCALING: TWO INSTANCES BEHIND ONE ENTRY POINT

GOAL: Two separate Node.js processes — both running your server — sharing one
      Postgres database and one Redis instance. Messages sent to one instance
      appear instantly on the other. This is the portfolio showpiece.

Think of it like two customer service agents at the same company.
They have access to the same customer files (database = Postgres) and the
same memo board (Redis). When one agent writes a memo ("Alice sent a message"),
the other agent sees it immediately.

Without the Redis adapter, the two agents work in separate offices with
separate memo boards. They never see each other's notes.

================================================================================

STEP 18.1 — UNDERSTAND WHY A PLAIN SETUP BREAKS
================================================================================

READ THIS CAREFULLY — it is the core concept for this entire part.

  Your server manages Socket.IO rooms in memory. When Alice's socket connects
  to Instance 1, that connection exists ONLY inside Instance 1's memory.

  Instance 2 has NO idea Alice is there.

  So if Bob is connected to Instance 2 and sends a message, Instance 2
  broadcasts it to everyone in the conversation room — but that room only
  contains Bob (on Instance 2). Alice, who is on Instance 1, never gets it.

  THE FIX — @socket.io/redis-adapter:
    When Instance 2 wants to broadcast to a room, instead of only broadcasting
    to its own sockets, it PUBLISHES the broadcast message into Redis.
    Instance 1 is SUBSCRIBED to that Redis channel.
    Instance 1 reads the message from Redis and delivers it to Alice.

    Two separate processes. One Redis channel in the middle. Every broadcast
    reaches every socket on every instance.

  You already installed @socket.io/redis-adapter in Part 15 (it was in the
  npm install redis @socket.io/redis-adapter command).
  You already created redisPublisher and redisSubscriber in redis/client.ts.
  Step 18.2 is simply: plug those clients into the Socket.IO adapter.

✅ DONE WHEN: You can say this in one sentence without looking:
  "Without the adapter, Instance 1's broadcasts don't reach sockets on Instance 2.
   The Redis adapter fixes this by publishing broadcasts through a Redis channel
   that all instances subscribe to."

STEP 18.4 — DEAL WITH STICKY SESSIONS
================================================================================

UNDERSTAND THE PROBLEM:
  Socket.IO starts with HTTP polling before it upgrades to a real WebSocket.
  During polling, the browser sends MULTIPLE separate HTTP requests.
  These requests must ALL go to the SAME server instance, because that instance
  has the in-progress handshake state in memory.

  If the load balancer sends Request 1 to Instance 1 and Request 2 to Instance 2,
  Instance 2 does not know about the handshake and the connection fails with
  mysterious errors like "session ID unknown" or "transport error".

  This is called the "sticky session problem" and it is the most common bug
  when deploying Socket.IO behind a load balancer.

TWO SOLUTIONS — PICK ONE:

──────────────────────── SOLUTION A (RECOMMENDED): Force WebSocket only ──────

  If you tell Socket.IO "never use polling, use only WebSocket", there is no
  polling phase, so there is nothing for the load balancer to mess up.

  This is the simpler solution. The only downside: very old browsers that do not
  support WebSocket cannot connect. In 2025+ this is rarely a real concern.

  WHERE TO SET THIS: On the CLIENT side (your React frontend), when you create
  the socket, add transports: ["websocket"]:

  const socket = io("http://localhost:4000", {
    auth: { token: getAccessToken() },
    transports: ["websocket"],   // ← Skip polling entirely
  });

  That is all. One line. The server does not need any changes.

──────────────────────── SOLUTION B: Sticky sessions in nginx ───────────────

  If you need polling to work (e.g. for compatibility), configure your load
  balancer to always send the same client to the same instance.
  This is called "sticky sessions" or "session affinity".

  In nginx, it looks like this (ip_hash = route the same IP to the same server):

  upstream chatapp_backend {
    ip_hash;
    server 127.0.0.1:4000;
    server 127.0.0.1:4001;
  }

  The downside: if one instance dies, clients that were "stuck" to it must
  reconnect and will hit a different instance, which may reset their session.

# Horizontal Scaling Decisions

## Sticky Session Strategy

**Decision:** Force WebSocket-only transport on the client.

**Why:** Socket.IO's HTTP polling fallback requires all requests from the same
client to land on the same server instance (sticky sessions). By forcing the
client to use only the WebSocket transport, we skip the polling phase entirely
and eliminate this problem.

**Trade-off:** Very old browsers without WebSocket support cannot connect.
This is acceptable for a modern chat app.

**Where to set it:** In the React frontend when creating the socket:
```js
const socket = io(SERVER_URL, {
  transports: ["websocket"],
  auth: { token: getAccessToken() },
});
```

## Instance Identification

Each instance is identified by the INSTANCE_NAME environment variable
(defaults to "instance-1" if not set).

To start two instances:
  Terminal 1: PORT=4000 npm run dev
  Terminal 2: PORT=4001 INSTANCE_NAME=instance-2 npm run dev

Both instances MUST connect to the same Neon branch and the same Redis.

COMMON PROBLEMS AND FIXES
================================================================================

PROBLEM: "Cannot find module '@socket.io/redis-adapter'"
FIX:     Run  npm install redis @socket.io/redis-adapter  in the backend folder.
         You should have done this in Part 15 but double-check.

PROBLEM: Redis adapter is attached but messages still don't cross instances.
FIX:     Check that BOTH instances use the SAME REDIS_URL.
         Run  echo $REDIS_URL  in both terminals to confirm.
         If one is empty, your .env is not being read — check for typos.

PROBLEM: "Session ID unknown" errors when connecting.
FIX:     You hit the sticky session problem. On your client, add:
           transports: ["websocket"]
         This skips polling entirely and solves the problem.

PROBLEM: Rate limiter is not blocking anything even after 20 messages.
FIX #1:  Check that redisClient is actually connected.
         Look for "[Redis:main] Connected." in the startup logs.
         If it is not there, fix Redis first (see Part 15 guide).
FIX #2:  Check your .env for REDIS_URL — it must not be empty and
         must start with  rediss://  (double s for TLS).
FIX #3:  Check that the import is correct in socketRateLimiter.ts:
           import { redisClient } from "../redis/client.js";
         The .js extension is required in ESM projects.

PROBLEM: "Cannot find name 'NOISE_LIMIT'" or similar TypeScript error.
FIX:     Make sure your import in message.ts or typing.ts includes all names:
           import { checkSocketRateLimit, MSG_LIMIT, MSG_WINDOW_S, NOISE_LIMIT, NOISE_WINDOW_S }
             from "../../utils/socketRateLimiter.js";

PROBLEM: The second instance fails to start with "Port already in use".
FIX:     You forgot to set PORT=4001 in the second terminal.
         The second terminal command must be:  PORT=4001 INSTANCE_NAME=instance-2 npm run dev

PROBLEM: General rate limiter blocks my own requests during development.
FIX:     Increase the limit temporarily while testing:
           max: 1000  ← just for local dev
         Or add your local IP to a skip list (see express-rate-limit docs for skip option).

PROBLEM: typescript error about "express-rate-limit" types.
FIX:     Run  npm install --save-dev @types/express-rate-limit
         Or, if express-rate-limit v7+ is installed, types are bundled — no separate install needed.
         To check: cat node_modules/express-rate-limit/package.json | grep types
